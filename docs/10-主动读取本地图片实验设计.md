# 主动读取本地图片：MCP → 插件 UI → ChatGPT 图片上下文

2026-09-21。状态：v1 工具与 UI 已实现，本地 14 项检查通过；网页首轮全自动识图验收通过（a/b 合计 18/18、missing 正确，用户确认无人工干预）。无引用与重复执行等后续实验继续进行。最新步骤和实际限制见 [自动读图实验记录](11-自动读图实验记录.md)。下文保留原实验设计。

## 目标与现有证据

用户已确认网页原生附件能够识图，不再测试手动上传基线。目标是在一次自然语言请求之后，由网页模型主动调用 Bridge 获取本地图片，自动将图片加入网页模型可用的视觉上下文。无需选择文件、拖拽附件或经过 GitHub。首轮允许网页内出现状态卡片；不承诺关掉网页后仍能执行。

现有 vision_probe：运行服务已经验证返回 PNG 字节正确；用户报告网页 a、b 仍不能识别。missing 正确报告无图。这说明当前直接图片内容块路径尚未满足需求，不能从中推断所有 MCP 客户端均不支持图片。

## 官方依据与核心假设

- https://developers.openai.com/plugins/build/chatgpt-ui ：imageIds 可将通过合法文件来源取得的图片 ID 提供给后续轮次；setWidgetState 是同步调用，不可将 await 它当作宿主已完成上下文更新的证明。
- https://developers.openai.com/plugins/reference#file-apis ：uploadFile 接受用户选择的文件并返回 fileId。文档没有保证从 MCP 字节构造的 File 可无点击自动上传，这正是本实验要验证的假设。
- UI 使用 MCP Apps 的资源关联、初始化和工具结果通知；ChatGPT 专有文件及状态能力先检测是否存在。

## 最小原型设计

拟新增 vision_widget_probe（尚未实现），参数 sample_id=a|b|missing、mode=auto|click、publish_images=true|false。首次只用服务环境现有合成样本，禁止读取答案文件。保留原 vision_probe 作对照。

工具关联版本化 UI 资源 ui://x14/vision-probe-v1.html。服务读取 PNG，返回两类数据：

1. content/structuredContent：run_id、sample_id、MIME、大小、SHA256、状态，不含视觉答案、图片 Base64 或本地路径。
2. 工具结果 _meta：供 UI 使用的 PNG Base64。该数据由宿主传入 UI，不要求网页 fetch localhost，不建立公网图片服务。

UI 从工具结果通知读取私有载荷，验证 MIME、长度和 SHA256，构造 File([bytes], neutralFilename, {type:'image/png'})。此步骤只是数据封装，不进行 OCR、图片分析或调用另一视觉模型。

auto 模式在收到样本且宿主接口就绪后，自动调用 uploadFile(file)，不指定 library:true；收到真实 fileId 后，调用 setWidgetState({modelContent: 无答案的样本标识与状态, privateContent: 最小诊断状态, imageIds: publish_images ? [fileId] : []})。绝不自行构造 fileId，绝不把非图片 ID 塞入 imageIds。

随后仅发送一次后续消息，要求读取本轮图片。优先 MCP Apps ui/message；兼容路径可检测 sendFollowUpMessage。单独记录请求是否被接受、模型是否实际续答。接口调用成功不代表模型已经看到图片。

UI 显示：本地图片已取得 → 文件登记已完成 → 图片引用已写入 → 已请求后续回答。最后不显示“识图通过”；通过与否由本地答案评分确定。失败显示阶段与原始错误的脱敏摘要。

## 分阶段实验与停止条件

| 实验 | 做法 | 要回答的问题 |
| --- | --- | --- |
| E0 宿主能力 | 加载卡片，检查 uploadFile、setWidgetState、后续消息能力和私有载荷 | 当前网页插件是否具备这条通道？ |
| E1 自动登记 | auto 读取 a，无点击构造 File 并上传 | 服务端来源的文件是否被接受？ |
| E2 自动识图 | E1 后写入 imageIds，自动请求后续回答 | 一次用户请求是否能完成本地图片识别？ |
| E3 时序诊断 | 仅当上传和状态写入成功、自动续答未识别时，用户只发送“继续读取当前图片” | 是否只是后续消息或上下文同步时机问题？ |
| E4 点击诊断 | 仅当自动上传失败时，点卡片里的“重试登记”按钮，使用同一份 Bridge 字节 | 是否要求用户手势？不弹文件选择器；成功也只算半自动 |
| E5 引用对照 | 新会话，用另一未知样本，上传后 imageIds=[] 再续答 | 是上传本身还是 imageIds 使图片可见？无引用却识别成功不直接归因于泄漏 |
| E6 稳定性 | 新会话运行 b、a，单独 missing；复用已完成 run_id 检查重复加载 | 是否读错图片、沿用旧图、重复上传或触发消息循环？ |

E0 缺能力立即报告具体缺项，不以图片预览替代模型识图。E1 被拒绝后最多进行一次 E4，不无限重试。E2 成功后才扩大图像大小和数量；PNG 首轮不引入 JPEG、PDF 等多变量。

missing 返回明确无图状态，UI 必须清空本卡片 imageIds、停止上传与自动续答；同一会话可能仍保留历史图片，因此模型应只报告当前样本无图，不声称历史图已从上下文删除。

## 防止假阳性与重复执行

答案只保留在 Bridge 服务环境，评分也通过该环境取得。此前当前终端与服务环境的同名路径内容不同，禁止使用终端旧答案评分。提示词、文件名、日志、modelContent 均不得包含答案。

每次结果有唯一 run_id，并记录样本 SHA256、UI 版本、模式、各阶段时间、能力检测、真实 fileId、自动/点击方式、后续消息状态及错误；不要记录 Base64 或临时下载凭据。多实例/刷新使用 run_id 与样本哈希去重；若上传结果不明，报告未知，不盲目再次上传。后续消息不得再次调用本工具，避免循环。

每张图按完整字符码 1 项、四象限颜色与形状 8 项评分。a、b 共 18/18、missing 正确、无答案旁路、从一次用户请求自动完成，才算本阶段全自动通过。部分识别单独记录，不能升级为通过。

## 通过后的实际文件路线

工具参数扩展为 project_id + 项目相对路径，复用项目授权并校验解析后的真实路径和链接目标。Bridge 读取本地或 SSH 文件并发送给 UI；UI 登记为 ChatGPT 图片，模型在后续轮次分析。保留文件大小限制、哈希和状态回报。

普通文件另设验收：CSV 是否真正进入网页分析工具、PDF 是文本读取还是页面视觉阅读。imageIds 只用于图片；不能从 PNG 成功推断 PDF、Excel 或任意文件自动分析成功。PDF 后续可由 Bridge 渲染页面图供同一路径分析，但原始 PDF 进入网页分析环境是另一项能力。
